## 0. 文档说明

### 0.1 详细设计与概要设计的关系

概要设计定义了"做什么"（模块/功能点/依赖），本设计定义"怎么做"（表结构/接口/规则表达式/状态机/**技术架构与技术路线**）。功能编号沿用概要设计（M<模块>-<序号>），一一对应，不新增功能，只展开细节。**换肤子系统（M18）是本次详细设计按需求新增的模块**，对应概要设计 M17 平台支撑的界面配置能力扩展。**技术架构与技术路线见第七部分（§26–§27）**：解决"用什么技术栈、怎么部署、技术怎么分期演进"。

> 阅读顺序建议：研发负责人先读第七部分（架构与路线），再读第二至六部分（表/接口/规则）；业务与产品可读第一部分规范 + 第六部分落地清单。

### 0.2 落地等级标记（重要）

全四期覆盖，但**并非所有模块都具备落地条件**。每个模块/接口标注落地等级，研发据此排期，售前据此承诺：

| 等级 | 含义 | 研发动作 | 售前口径 |
|---|---|---|---|
| **L1 可直接开发** | 依赖清晰、规则明确、无外部阻塞 | 立即进入编码 | 可写进一期合同 |
| **L2 方案级** | 设计完整，但依赖外部条件未满足 | 完成设计，待条件激活后开发 | 只做预授权，不承诺交付时间 |
| **L3 待触发** | 依赖政策发布/厂商配合/付费验证 | 保留设计，不投入开发 | 不进当期合同 |

> **一期可落地清单 = 所有 L1 模块**；L2/L3 模块详设只保证"条件满足后可直接进入编码"，不代表现在能交付。这不是设计不完整，是诚实标注依赖（对应定位 v0.4 §4.5 售卖红线）。

# 第一部分 总体设计规范

## 1. 命名与编码规范

| 对象 | 规范 | 示例 |
|---|---|---|
| 数据库表 | 小写下划线，业务域前缀 | `sync_task`、`qtl_issue`（质量域）、`risk_point` |
| 字段 | 小写下划线，布尔用 `is_` 前缀，时间用 `_at` 后缀 | `is_deleted`、`created_at` |
| 主键 | 统一 `id`，字符串 UUID（离线环境避免自增冲突） | `id VARCHAR(36)` |
| API 路径 | `/api/v1/<域>/<资源>`，复数资源名 | `/api/v1/sync/tasks` |
| 功能编号 | `M<模块>-<序号>`，与概要设计一致 | `M1-03` |
| 错误码 | 5 位数字，见 §4 | `30004` |

**业务域前缀**：`sync_`（接入同步）/`gov_`（治理）/`rule_`（规则）/`sim_`（模拟）/`fix_`（整改）/`biz_`（经营）/`rat_`（评级）/`ai_`（AI）/`prof_`（画像）/`sys_`（平台）/`ui_`（换肤）。

## 2. 公共字段（所有业务表必含）

```sql
id            VARCHAR(36)   NOT NULL COMMENT '主键UUID',
tenant_id     VARCHAR(36)   NOT NULL COMMENT '医院/租户ID，数据隔离',
created_at    DATETIME      NOT NULL COMMENT '创建时间',
updated_at    DATETIME      NOT NULL COMMENT '更新时间',
created_by    VARCHAR(36)   COMMENT '创建人',
updated_by    VARCHAR(36)   COMMENT '更新人',
is_deleted    TINYINT       NOT NULL DEFAULT 0 COMMENT '逻辑删除0否1是',
version       INT           NOT NULL DEFAULT 0 COMMENT '乐观锁版本'
```
> 审计敏感表（审计日志、工单、规则变更）**禁止物理删除**，仅逻辑删除 + 全量留痕。

## 3. API 设计规范

- **协议**：HTTPS（内网可配 HTTP + 国密），JSON 交互，UTF-8
- **鉴权**：Bearer Token（在线）/ 离线授权文件签名校验（内网隔离，见 M17-01）
- **统一响应包**：
```json
{ "code": 0, "message": "ok", "data": {}, "traceId": "uuid", "timestamp": 1731000000 }
```
- **分页**：`page`（从1开始）+ `pageSize`（默认20，上限200），响应带 `total`
- **幂等**：写操作带 `Idempotency-Key` 请求头，重复提交返回首次结果
- **租户隔离**：所有接口强制从 Token 解析 `tenant_id`，请求体中的 tenant_id 一律忽略
- **越权防护**：模块未授权时返回 `20004`，不返回"功能不存在"以外的信息（防探测）

## 4. 统一错误码表

| 码段 | 域 | 代表码 |
|---|---|---|
| 0 | 成功 | `0` ok |
| 1xxxx | 参数与请求 | `10001` 参数缺失 / `10002` 参数格式错误 / `10003` 分页越界 |
| 2xxxx | 认证授权 | `20001` 未登录 / `20002` Token过期 / `20003` 无权限 / `20004` 模块未授权 / `20005` 租户越界 |
| 3xxxx | 接入同步 | `30001` 数据源连接失败 / `30002` 授权文件无效 / `30003` 同步任务不存在 / `30004` 同步中断 / `30005` 对账差异超限 / `30006` 字段白名单为空 |
| 4xxxx | 治理与规则 | `40001` 口径未定义 / `40002` 规则语法错误 / `40003` 规则包未下发 / `40004` 数据元缺失 |
| 5xxxx | 模拟与报告 | `50001` 模拟类型不支持 / `50002` 依赖数据不足 / `50003` EMR全文不可得已降级 / `50004` 报告生成失败 |
| 6xxxx | 整改闭环 | `60001` 问题单不存在 / `60002` 状态非法流转 / `60003` 复核未通过 |
| 7xxxx | 经营分析 | `70001` DRG分组系统未就绪 / `70002` 成本数据不可得 / `70003` 成本粒度不足已降级 |
| 8xxxx | 评级与AI | `80001` 标准未发布 / `80002` 误报率超阈值 / `80003` 评测集未通过 |
| 9xxxx | 平台与换肤 | `90001` 主题不存在 / `90002` 品牌配置未生效 / `90003` 配置缓存刷新失败 / `99999` 系统内部错误 |

> 错误码为**全局常量**，前后端共用枚举文件，禁止业务代码硬编码数字。每个错误码必须配可读的 `message` 和处理建议（前端据此决定是否引导用户）。

# 第三部分 API 接口详细设计

## 12. 一期接口（L1 可直接开发）

### 12.1 M1 接入同步

| 接口 | 方法/路径 | 请求 | 响应 | 权限 | 错误码 |

# 第四部分 业务规则与状态机详细设计

## 14. 核心业务规则表达式

> 以下为可执行规则的逻辑表达（SQL 伪代码），研发据此实现为 M5 的 SQL/逻辑规则。规则参数（天数、占比）应配置化，不硬编码。

### 14.1 飞检规则（M7，对应定位第五章映射表）

**R-FJ-01 分解住院**
```sql
SELECT patient_ref, diag_code, adm_date, dis_date
FROM gov_visit v
WHERE EXISTS (
  SELECT 1 FROM gov_visit v2
  WHERE v2.patient_ref = v.patient_ref
    AND v2.adm_date > v.dis_date
    AND DATEDIFF(v2.adm_date, v.dis_date) <= :interval_days      -- 默认15
    AND LEFT(v2.diag_code,3) = LEFT(v.diag_code,3)               -- ICD-10前三位一致
    AND NOT EXISTS (                                              -- 无并发症/合并症进展证据
      SELECT 1 FROM gov_diagnosis d WHERE d.visit_id = v2.id AND d.type IN ('COMPLICATION','COMORBID')
    )
)
-- 命中 → 风险点（违规类型=分解住院，证据=两次住院记录）
```

**R-FJ-02 低标准入院**
```sql
SELECT v.* FROM gov_visit v
JOIN gov_diag d ON d.visit_id = v.id
JOIN gov_bill b ON b.visit_id = v.id
WHERE d.diag_code IN (SELECT code FROM dict_outpatient_treatable)   -- 门诊可治疗病种清单
  AND (b.baseline_infusion_fee + b.oral_drug_fee) / b.total_fee > :ratio  -- 默认0.70
  AND NOT EXISTS (SELECT 1 FROM gov_record r WHERE r.visit_id=v.id AND r.type IN ('RESCUE','OPERATION'))
-- 命中 → 风险点（违规类型=低标准入院）
```

**R-FJ-03 低码高编（语义辅助，依赖 EMR 全文）**
```
输入：病案首页主诊断编码 D1、手术编码 S1；EMR 病程记录/手术记录文本 T
处理：语义模型比对 — 编码权重 vs 临床文本证据
IF 编码权重(D1) > 文本支持度(T) * :threshold  → 提示（人工复核，不作独立预警）
依赖：need_emr_fulltext = 1
降级：EMR 全文不可得 → 转 R-FJ-03b（仅比对结构化字段，报告标注降级 50003）
```

**R-FJ-04 重复收费 / 分解收费**
```sql
SELECT b.* FROM gov_bill b
JOIN gov_order_exec e ON e.order_ref = b.order_ref
WHERE (互斥项目组标记 = 1 AND 同医嘱对应多个互斥收费项)
   OR (术式收费项目 NOT IN 对应手术操作记录)
-- 命中 → 风险点
```

**R-FJ-05 超限定支付用药（事前提醒补充）**
```sql
SELECT o.* FROM gov_order o
JOIN gov_diag d ON d.visit_id = o.visit_id
JOIN dict_medical_insurance m ON m.drug_code = o.drug_code
WHERE d.diag_code NOT IN (m.limited_payment_scope)
  AND NOT EXISTS (SELECT 1 FROM gov_approval a WHERE a.order_ref=o.id AND a.type='SPECIAL')
-- 命中 → 事前提醒（定位为院内多源维度补充）
```

### 14.2 数据质量规则（M3，五维度）

| 维度 | 规则表达式（伪代码） | 阈值参数 |
|---|---|---|
| 唯一性 | `COUNT(*) - COUNT(DISTINCT patient_visit_key) <= :tol` | tol=0 |
| 完整性 | 必填字段空值率 `NULL_COUNT(required_fields)/total <= :tol` | tol=0（首页必填） |
| 合规性 | 编码值 `IN` 标准字典，否则记不合规 | 字典版本 |
| 同一性 | 三源比对 `首页.诊断 ≠ 医保结算.诊断 ≠ EMR.出院诊断` 记不一致 | 一致率≥80% |
| 时效性 | 出院→首页归档天数 `<= :days`；结算清单上传时限达标 | days=N（院方定） |

> 五维度加权得质量分；任一否决线项达标率 <80% 触发 `is_veto` 预警（对应定位第二章数据质量单项否决）。

### 14.3 风险优先级评分模型（M6-04）

```
priority_score =
    w1 × 违规金额预估(归一化)
  + w2 × 扣分影响(归一化)
  + w3 × 发生频次(归一化)
  + w4 × 证据确凿度(0-1)
  + w5 × 历史整改状态(未整改加权)
其中 w1..w5 为可配置权重，默认 w1=0.3, w2=0.3, w3=0.15, w4=0.15, w5=0.1
排序规则：score 降序，同级按违规类型严重度排序
要求：权重与得分明细对授权用户可见（可解释）
```

### 14.4 国考指标计算口径（M8，节选）

| 指标 | 计算口径 | 一致性硬要求 |
|---|---|---|
| CMI | `Σ(RW_i) / 病例数`（RW 来源见 M4 口径登记） | 与官方上报口径一致率 100% |
| 四级手术占比 | `四级手术例数 / 手术总例数 × 100%` | 同上 |
| 低风险死亡率 | `低风险组死亡例数 / 低风险组病例数` | 同上 |
| 平均住院日 | `Σ(出院日−入院日) / 出院病例数` | 同上 |

> 推演沙盘（M8-04）：调整单指标假设 → 按权重估算对总分/排名影响，**结果必须标注"估算"并给出置信口径**，禁止表述为确定结论（C6）。

### 14.5 结余计算口径（M10，L2）

```
结余 = 收入 − 成本
成本粒度 = DISEASE（病种级）：成本归集到病种，结余精确到病种
成本粒度 = DEPT（科室级）：降级为科室级粗算，结余标注"估算"，触发 70003
亏损归因：
  IF 费用结构异常(费用>同组P90) → '费用失控'
  ELSE IF 入组偏低(RW<同组均值×0.8) → '入组偏低'
  ELSE → '成本失控'
```

# 第五部分 换肤与品牌定制子系统（M18）详细设计

> 本模块按需求新增，落地等级 **L1**（一期即可开发）。目标：一套配置同时支持**用户自主切换主题**和**医院品牌定制**，两者不冲突、可叠加。

## 16. 需求边界与设计原则

| 能力 | 说明 | 作用范围 |
|---|---|---|
| 主题切换 | 浅色 / 深色 / 护眼（暖色低蓝光），用户随时切换，即时生效 | 用户个人，持久化偏好 |
| 品牌定制 | 医院 Logo、主色调、系统名称、登录页背景 | 租户级（全院统一），实施配置 |
| 叠加规则 | 品牌主色注入到主题的语义色变量，主题（明/暗）决定表面色与文字色 | 主题 × 品牌 = 最终皮肤 |

**设计原则**：
1. **语义色变量，不是硬编码色值**：界面只引用语义变量（如 `--brand-primary`、`--surface-bg`），主题和品牌都只改变量值，不改组件代码。
2. **品牌定制不破坏可读性**：品牌主色由实施在配置时做对比度校验（与背景对比度 ≥4.5:1），校验不通过拒绝保存（返回 90002）。
3. **护眼主题是独立主题不是滤镜**：有完整的语义色映射，保证图表、报告、警告色在护眼主题下仍可辨（警告色不因主题改变语义）。
4. **配置集中、下发缓存**：租户品牌配置存服务端，前端启动拉取并缓存，切换主题为纯前端行为（离线可用）。

### 17.3 主题切换机制

```
1. 用户点击主题切换 → 前端写 ui_user_pref.theme_code（本地 localStorage + 同步服务端）
```

## 18. 品牌定制（Brand）设计

### 18.1 可定制项

| 配置项 | 类型 | 约束 | 存储 |
|---|---|---|---|
| 系统名称 | 字符串 | ≤30 字符 | `ui_brand_config.system_name` |

| 页脚备案信息 | 字符串 | ≤100 字符 | `footer_text` |

### 18.2 主色注入算法

```
输入：tenant.primary_color（品牌主色，如 #1E5AA8）
处理：
  1. 对比度校验：与 --surface-bg 对比度 ≥ 4.5:1，否则拒绝（90002）
  2. 派生色阶：由主色生成 hover/active/disabled 三档（明度 ±10%/15%）
  3. 注入：运行时设置 CSS 变量 --brand-primary 及其派生色
输出：全站主色统一切换，图表主色同步
边界：警告/风险语义色（--color-warning/--color-danger）不被品牌主色覆盖，保证风险提示语义不变
```

### 18.3 品牌配置生效流程

```
实施在管理后台配置品牌 → 服务端校验（图片规格、对比度）→ 保存 ui_brand_config
→ 前端下次启动拉取（或缓存刷新接口 §18.4）→ 注入主色 + 加载 Logo
→ 全院用户生效（用户个人主题偏好仍保留，叠加在品牌之上）
```

| 获取品牌配置 | GET `/api/v1/ui/brand` | — | system_name, logo_ref, primary_color, derived | 90002 |
| 保存品牌配置 | PUT `/api/v1/ui/brand` | 可定制项 | contrast_checked | 90002 |
| 刷新配置缓存 | POST `/api/v1/ui/brand/refresh` | — | ok（通知前端重载） | 90003 |
| 获取我的偏好 | GET `/api/v1/ui/pref` | — | theme_code, font_scale | — |
| 保存我的偏好 | PUT `/api/v1/ui/pref` | theme_code, font_scale | ok | 90001 |

**示例：保存品牌主色（含对比度校验）**
```
PUT /api/v1/ui/brand
{ "primary_color":"#1E5AA8", "system_name":"XX医院运营决策平台" }
→ 对比度校验通过: 200 { "code":0, "data":{"contrast_checked":1, "primary_derived":{"hover":"#2A6BC0",...}} }
→ 校验失败:       400 { "code":90002, "message":"主色与背景对比度不足4.5:1，请调整" }
```

## 21. 换肤边界与注意

- **报告导出物不随主题变色**：模拟报告、佐证包导出为固定浅色版式（打印/存档需要），主题只影响在线界面。
- **风险色语义锁定**：无论主题/品牌，风险、否决、警告色语义不变（见 §17.2），避免护眼或品牌定制弱化风险提示。
- **品牌配置不覆盖租户外**：品牌配置严格按 tenant_id 隔离，越界访问返回 20005。
- **审计留痕**：品牌配置变更记入 `sys_audit_log`（改了什么、谁改的）。

### 26.2 技术栈选型（通用栈优先）

| 层次 | 推荐选型（通用栈） | 信创适配替代（后置） | 说明 |
|---|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite + Element Plus + ECharts | 同（浏览器兼容麒麟自带浏览器/Chrome内核） | 换肤依赖 CSS 变量方案（§17.2），Vue 原生支持 `data-theme` 属性切换 |
| 后端 | Java 17 + Spring Boot 3 + Spring Cloud Gateway + MyBatis-Plus | 同（JDK 用国产 JDK 如毕昇/龙井，需验证） | 业务服务按模块分包，一期可单体部署降低运维成本，二期按域拆微服务 |
| 平台库 | MySQL 8.0 | 达梦 DM8 / 人大金仓 KingBase（经适配层） | 公共字段/类型按 MySQL 设计（§2），信创库做类型映射 |
| 院内同步库 | MySQL 8.0（只读副本，字段白名单） | 达梦/KingBase（同步工具需支持 CDC 采集） | 同步库与平台库物理分离，与生产性能隔离（定位 §9.2） |
| CDC 采集 | Debezium（MySQL/PG binlog）为主，Canal 备选 | 依赖国产库 CDC 能力（达梦/KingBase 日志解析，需 POC 验证） | 断点续传依赖 checkpoint（§5.3），采集器需厂商订阅授权 |
| 缓存 | Redis（规则包缓存、会话、看板聚合结果） | 国产 Redis 兼容版（如 Tair/国产中间件） | 非必需，一期可先用数据库 |

| 调度 | XXL-JOB（同步/规则/对账定时任务，对应 M17-04） | 同 | 支持失败重试、告警、分片 |
| AI/语义 | 院内可部署的开源大模型（Qwen/GLM 等）经 AI 网关调用 | 同（国产模型天然适配信创） | **数据不出院**：民营版仅脱敏文本上云，公立版院内推理（C2） |
| 网关/认证 | Spring Cloud Gateway + JWT + 离线授权文件双模式（§11.1） | 同 | 适应内网隔离，未授权模块返回 20004 |
| 容器/部署 | Docker Compose（院内私有化）/ Kubernetes（民营云化） | 国产容器平台/信创云（后置） | 双形态统一镜像，靠编排配置切换（见 §26.4） |

### 26.3 双形态统一部署架构

**核心设计**：一套代码、一套镜像，**部署拓扑与数据落位靠配置切换**，不因公立/民营分叉出两套产品（对应第三章"同一套底座，两种打法"）。

**形态 A｜公立院内私有化（含同步库）**
```
[院内网络·隔离区]
  ├─ 生产域（厂商运维）：HIS/EMR/病案/医保/收费 —— 只开放 binlog/OGG 订阅或只读视图
  ├─ 同步域（我方运维）：CDC 采集器 + 院内同步库（最小字段集，脱敏，几十 GB）
  └─ 平台域（我方运维）：应用服务集群 + 平台库 + Redis + 调度 + AI 推理节点
  网络：全域院内，数据不出院；授权走离线文件 + 在线校验双模式
  资源：需院方提供同步库与平台服务器/存储（对应定位 §9.2 四项代价之一，报价须明确）
```

**形态 B｜民营云化（多租户 SaaS）**
```
[民营医院现场]  本地同步库（最小字段集，脱敏）→ 仅上传脱敏结果与特征
        │  （原始数据不出院，C2）
        ▼
[云端· Kubernetes]  多租户平台服务共享集群 + 租户隔离（tenant_id 强制，§3/§7）
  ├─ 网关/认证/审计/调度（共享）
  ├─ 规则引擎 + AI 网关（共享，按租户授权加载规则包）
  └─ 各租户平台库（schema 或库级隔离）
```

| 对比项 | 形态 A 公立私有化 | 形态 B 民营云化 |
|---|---|---|
| 部署位置 | 全院内部署（同步库+平台） | 现场同步库 + 云端平台 |
| 数据落位 | 全部数据不出院 | 原始不出院，脱敏结果上云 |
| 租户模型 | 单租户（一院一实例） | 多租户共享（tenant_id 隔离） |
| 编排方式 | Docker Compose（轻量化，适配内网） | Kubernetes（弹性、批量复制） |
| AI 推理 | 院内节点本地推理 | 云端推理（仅脱敏文本） |
| 授权方式 | 离线授权文件为主 | 在线校验为主 |
| 共同点 | 同一套镜像、同一分层架构、同一规则包体系、同一换肤子系统 | 同左 |

> **部署判定**：两套形态共用镜像与代码，差异收敛到配置中心（§M17-05）的部署 profile 与租户隔离策略。研发不得为单一形态写死逻辑，否则违背"双形态统一"决策。

### 26.4 关键技术方案

| 技术点 | 方案 | 对应功能/约束 | 风险控制 |
|---|---|---|---|
| 唯一系统边界 | L1 只订阅生产变更；同步库只读副本，零写回生产 | C1、M1、定位 §9.2 | 生产库账号仅授予订阅/只读权限，写操作全部落我方库 |
| CDC 增量同步 | Debezium/Canal 捕获 binlog，按字段白名单映射写入同步库 | M1-02/03、§5.2 | 字段白名单默认全不选；厂商订阅授权书面确认（M1-01） |
| 断点续传与对账 | checkpoint 位点 + 日级全量/增量对账，差异超限告警 | M1-06/07、§5.4 | 中断不丢数据，恢复按断点续传；差异率阈值可配 |
| 脱敏管道 | 同步落库前哈希/掩码，同步库无明文 PHI | C2、M1-05 | 抽检同步库无明文身份信息（验收口径） |
| 多租户隔离 | 所有请求从 Token 强制解析 tenant_id，请求体中的一律忽略 | §3、§7.1、M17-03 | 跨租户访问返回 20005；审计日志记录租户 |
| 规则引擎 | SQL/逻辑规则自研执行器 + 语义规则经 AI 网关（人工复核） | M5、§14 | 语义规则不作独立预警（C6）；规则包按授权加载 |
| 数据血缘 | 风险点→规则→口径→数据元→源字段全链可追溯 | M4、§5 数据模型 | 支撑"检查视角可解释"与报告免责声明 |
| 授权中心 | 离线授权文件签名 + 在线校验双模式，控制开关 | M17-01、§7.2、§15.4 | 未授权模块入口隐藏、规则包不下发、接口不响应 |
| 审计 | 全量操作日志不可篡改，禁物理删除 | M17-02、§11.2 | 谁在何时读写了什么全留痕 |
| 换肤 | 语义色 CSS 变量 + 品牌主色运行时注入 | M18、§16-21 | 风险色语义锁定；报告导出固定浅色 |
| AI 集成 | 经 AI 网关调用，设误报率阈值 + 评测集 + 人工复核 | M14、§14.3 | 误报率超限不得开放；回答附来源避免幻觉 |

### 26.5 信创适配方案（后置）

> 原则：不因信创推迟 P1 交付。通过**适配层**屏蔽差异，待通用栈跑通、有明确信创验收要求的项目再逐项替换。

| 适配层 | 通用栈 | 信创替代 | 适配工作量/风险 |
|---|---|---|---|
| CPU/服务器 | x86（Intel/AMD） | 鲲鹏/飞腾（ARM）、海光/兆芯 | 中：JDK 与原生依赖需 ARM 版本验证 |
| 操作系统 | CentOS/Ubuntu | 麒麟、统信 UOS | 低：Java 应用基本无感，验证脚本/字体 |
| JDK | OpenJDK 17 | 毕昇/龙井等国产 JDK | 低-中：验证 Spring Boot 3 兼容性 |
| 数据库 | MySQL 8.0 | 达梦 DM8、人大金仓 KingBase | **高**：SQL 方言、类型映射、CDC 采集能力需 POC |
| 中间件 | Redis、XXL-JOB、K8s | 国产兼容版 | 中：接口兼容性验证 |
| 浏览器 | Chrome/Edge | 麒麟自带/国产浏览器 | 低：前端做内核兼容测试 |

**适配路径**：抽象数据库访问层（MyBatis-Plus 方言可插拔）→ 提供达梦/KingBase 类型映射配置 → CDC 采集器针对国产库做 POC → 获取信创兼容性认证。**CDC 对国产库的支持是最大不确定项**，须在首个信创项目启动前完成技术验证（列入 §27.5 风险）。

| L2 治理底座 | M2/M3/M4 归一化/质量/同一性 | 治理服务 + 口径字典 |
| L1 接入同步 | M1 接入同步 | CDC 采集器 + 脱敏管道 + 调度 |
| 贯穿 M17 | 授权/审计/用户/调度/配置 | 网关 + 认证 + 审计服务 + XXL-JOB + 配置中心 |

## 27. 技术路线

### 27.1 演进总原则

1. **通用栈先行**：P1 用成熟通用开源栈快速跑通闭环，不为未到来的信创需求付出早期成本。
2. **信创后置可插拔**：通过适配层保留替换能力，接到信创验收要求再逐项替换（§26.5）。
3. **架构随依赖解锁**：P2a 经营分析依赖院内 DRG/成本系统就绪，技术投入与该依赖的实际可得性绑定，不做无依赖空转。
4. **能力可降级**：每个外部依赖都有降级形态（概要 §0.3），技术路线不假设依赖一定到位。

### 27.2 分期技术演进路线

| 期 | 技术重点 | 本期引入的技术组件 | 架构影响 | 交付判定（技术侧） |
|---|---|---|---|---|
| **P1 底座期** | 打通同步→治理→模拟→整改主链 | Vue3/Spring Boot/MySQL/Debezium/规则执行器/网关认证/审计/XXL-JOB | 确立 L0/L1 唯一边界与同步库方案；单体部署 + Docker Compose | 三源同步对账通过 + 跑出被认可的模拟飞检报告 + 全链可追溯 |
| **P2a 经营期** | 结余分析→科室画像→驾驶舱的依赖链 | 只读接入 DRG 分组结果/成本数据；指标聚合与看板缓存（Redis） | 新增只读经营数据接入（IF-DRG/IF-HRP），不改主链边界 | 结余口径与医院核算偏差在阈值内；驾驶舱 3 次点击内可答 |
| **P2b 条件期** | AI 语义质控、数智评级规则库 | AI 网关 + 院内大模型；评级规则包（标准发布后加载） | 新增 AI 网关旁路（人工复核）；评级走预授权开关 | 语义质控误报率达标方可开放；数智标准发布后规则包可下发 |
| **P3 生态期** | 个人画像、医生工作站嵌入 | 厂商实时接口直读通道（唯一写回生产） | 引入第三条数据通道（实时直读，非同步库），须厂商协议 | 付费意愿验证通过 + 厂商接口协议签署 |

> **关键约束**：P3 的工作站提醒**不能复用同步库**（CDC 秒~分钟级延迟撑不了事中拦截），必须走厂商实时接口直读——这是 P3 才做、且强依赖厂商配合的技术根因（对应 M16 定位张力提示）。

### 27.3 关键选型决策与备选

| 决策点 | 推荐方案 | 备选方案 | 选择理由 | 触发切换条件 |
|---|---|---|---|---|
| 后端架构 | 一期单体（模块化分包） | 二期按域拆微服务 | 一期降低运维成本，模块边界已清晰便于后续拆分 | 团队规模扩大 / 单实例性能瓶颈 |
| 数据库 | MySQL 8.0 | PostgreSQL / 达梦 | 生态成熟、CDC 工具支持好、招人容易 | 信创验收要求 → 达梦（走适配层，先 POC） |
| CDC 工具 | Debezium | Canal（MySQL）/ 数据库原生复制 | Debezium 多源支持好、社区活跃 | 院内源库不许开 binlog → 只读视图/定期导出降级（频率降低） |
| 规则引擎 | 自研 SQL/逻辑执行器 | Drools | 规则以 SQL/阈值为主，自研更可控、无额外学习成本 | 规则复杂度显著上升（大量决策表/推理）→ 评估 Drools |
| 语义质控 | 院内开源大模型 + 人工复核 | 规则比对（无模型） | 结构化字段不足时补语义维度，但严控误报 | 误报率超阈值 → 关闭为独立预警，仅作提示 |
| 部署编排 | 院内容器 Compose / 云端 K8s | 裸机部署 | 统一镜像、配置切换 | 院内无容器环境 → 裸机 + 脚本部署 |
| AI 部署位置 | 公立院内推理 / 民营脱敏上云 | 全院内推理 | 平衡成本与数据不出院约束 | 数据合规要求收紧 → 一律院内推理 |

### 27.4 国产化（信创）演进路径

| 阶段 | 目标 | 前置条件 | 产出 |
|---|---|---|---|
| 阶段一·通用栈上线 | P1-P2 在通用栈稳定交付，跑通标杆 | 无 | 成熟产品 + 可复制实施 |
| 阶段二·兼容适配 | 完成达梦/KingBase + 麒麟/统信适配 POC | 有明确信创项目需求 | 适配层配置 + 兼容性清单（§26.5） |
| 阶段三·信创交付 | 通过信创兼容性认证，可参与信创招标 | 阶段二 POC 通过 + CDC 国产库支持验证 | 信创版镜像 + 认证材料 |

> **最大风险点**：CDC 对国产数据库的变更捕获支持。若达梦/KingBase 的日志解析能力不足，需降级为"只读视图 + 定时抽取"（频率降低，延迟变大），此时须重新评估对事后报告是否够用。**此风险须在首个信创项目启动前完成 POC 验证**（M1 全链依赖）。

### 27.5 技术风险与应对

| 风险 | 影响 | 等级 | 应对 |
|---|---|---|---|
| 厂商不开 binlog/订阅权限 | M1 同步链无法启动 | 阻塞级 | 降级只读视图/定期导出；售前 9.3 尽调提前确认，写入合同前提 |

| 同步库存储资源未落实 | 院内无存储，方案落地受阻 | 阻塞级 | 售前明确资源由谁承担（待决 Q2），报价计入 |
| 信创库 CDC 支持不足 | 阶段三信创交付受阻 | 高（后置） | 提前 POC；不支持则降级抽取频率并评估够用性（§27.4） |

| 双形态代码分叉 | 维护两套产品，违背统一决策 | 中 | 强制共用镜像与配置切换，代码评审拦截形态硬编码 |
